# 代码规范（simple_olap）

本规范用于统一项目内的**注释风格**与**代码组织方式**，目标是提升可读性。
规范不改变任何运行逻辑与既有缩进/排版（缩进与排版以 clang-format 为准，不在本规范讨论范围）。

## 1. 文件组织

每个源文件按固定顺序组织，便于快速定位内容：

1. `#pragma once`（头文件）或文件级说明注释
2. `#include`：标准库在前，项目内头文件在后，各自按字母序排列，组间空行分隔
3. 文件/模块级说明注释（见第 3 节）
4. `namespace simple_olap {`
5. 匿名 `namespace {`：仅本文件可见的辅助函数（若存在），放在所有对外定义之前
6. 对外定义的实现，按第 2 节分类排序

## 2. 函数分类与排序

同一文件内的函数按「生命周期 → 主流程 → 辅助」的逻辑分组排列，组间以注释分隔：

- **构造函数 / 静态工厂 / 析构函数**：对象生命周期相关，放最前
- **核心业务流程**：按调用链顺序排列（如 写路径 → 读路径），与读者理解顺序一致
- **观察接口 / 访问器**：只读查询用的小接口，放核心流程之后
- **私有辅助函数**：仅供本文件/本类内部调用，放最后

头文件中 `public` / `private` 分区内的成员同样遵循上述顺序。

### 分组分隔注释

使用统一的分隔注释标记分区，两级标题含义不同：

```cpp
// ==========================================
// 模块级标题（一个文件/大类的说明）
// ==========================================

// ---------- 分区标题（一个逻辑分组） ----------
```

不要在同一文件内混用其它风格的分隔线（如仅有 `====` 无标题、或不同长度的 `----`）。

## 3. 注释规范

### 3.1 语言与语气
- 同一文件内注释语言保持一致；本项目以**中文**为主，新增或调整的注释优先用中文。
- 已有的英文注释若表达清晰，不必为了统一而逐条翻译，避免无谓改动。
- 面向「为什么」而非「是什么」：解释设计意图、约束、易错点；不复述代码字面含义。
- 对显而易见的代码（如 `i++`、简单 getter）不写注释。

### 3.2 长度与复杂度
- 单条注释保持简短：一般 1 行，复杂约束最多 3~4 行。
- 避免把一句话拆成多行硬换行（如每行只有几个字）。整句写完再换行。
- 避免在注释里写临时思考、口语化疑问（如「实际上不需要，但是……」）；要么删除，要么改为明确的结论。

### 3.3 类型
- **文件/模块头注释**：说明该文件职责、与他人协作的边界（供新读者快速建立心智模型）。
- **公共 API 注释**（头文件对外方法）：说明语义、参数约束、返回值含义、失败条件。
- **实现注释**（.cpp）：解释关键步骤、为何这样做、陷阱与不变量。
- **不变量注释**：对并发/生命周期/魔法值等，明确指出必须满足的前提。

### 3.4 格式
- 行内/单行注释使用 `//`；不使用 `/** ... */` 包裹仅一句话的说明。
- 注释与代码保持同样缩进；注释行紧跟其解释的代码之前。
- 中文与英文/数字之间保留一个空格（如 `读取 32 位无符号整数`）。

## 4. 命名与其它

- 类型：`PascalCase`；函数/变量：`snake_case`；常量：`k` 前缀 + `PascalCase`（如 `kMaxSegmentRowCount`）。
- 头文件包含路径用相对路径，先从最近模块开始。
- 魔法值（如游标初始 `uint32` 最大值）必须由注释说明其含义与前提。
- 除非逻辑需要，不新增注释掉的「死代码」；确需保留的历史实现应注明原因与移除条件。

## 5. 修改约束（重要）

整理代码时**只做**以下改动，保持行为与排版不变：
- 调整注释的措辞、长度、复杂度与一致性
- 按第 2 节重新排列函数顺序
- 增加分组分隔注释

**不得**借此重排逻辑、修改变量名或变更格式/缩进。
